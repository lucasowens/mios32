## #35 — "NonBlocking" UART send busy-waits on the +4 emission task

**Verdict:** HOLD

**Anchors:** mios32/common/mios32_uart_midi.c: MIOS32_UART_MIDI_PackageSend_NonBlocking (function 260-316; blocking put at 306; dead -2 case at 308; RS mutations at 276/295/302-303; header contract 256-257), MIOS32_UART_MIDI_PackageSend (327-334, while(==-2) at 331), MIOS32_UART_MIDI_RS_Reset (194-209). mios32/STM32F4xx/mios32_uart.c: MIOS32_UART_TxBufferPutMore_NonBlocking (665-703, reject at 673), MIOS32_UART_TxBufferPutMore (716-723, THE spin at 720), MIOS32_UART_TxBufferPut_NonBlocking (736-741, misnamed sibling), MIOS32_UART_TxBufferFree (589-599). mios32/common/mios32_midi.c: MIOS32_MIDI_SendPackage (510-561, UART dispatch at 538), MIOS32_MIDI_SendPackage_NonBlocking (446-497, UART dispatch at 474). modules/sequencer/seq_midi_out.c: SEQ_MIDI_OUT_Handler (632, fire-and-forget send at 655), SEQ_MIDI_OUT_FlushQueue (573-587, send at 579), callback default at 189-193. apps/sequencers/midibox_seq_v4/core/app.c: SEQ_TASK_MIDI (842-860, MUTEX_MIDIOUT_TAKE at 845). apps/sequencers/midibox_seq_v4/mios32/tasks.c: PRIORITY_TASK_MIDI tskIDLE+4 (56), xTaskCreate (90).

**Risks / reachability:** Deferred, not fixed. Reachability today: requires a >64-byte burst to ONE DIN port within a drain window (~25-30 note events with RS optimisation on, fewer with it off or with CC/clock mixed in); the fork is deliberately heading into dense multi-track DIN emission ('next ceiling ~8-track emission'), so exposure grows. Files ARE compiled into the app build (core MIOS32 + shared sequencer module). Any fix changes cross-port drain ordering (head-of-line: a saturated DIN head item delays USB items behind it by >=1ms) and touches FlushQueue's guaranteed-note-off semantics - both need by-ear/DIN-analyzer validation that the USB-centric HIL harness cannot observe (RS correctness on the wire, no stuck notes on stop under saturation).

**Full derivation & fix plan:**

MECHANISM (all verified against current source, 2026-07-02). Call chain: TASK_MIDI @ tskIDLE+4 (tasks.c:56/90) -> SEQ_TASK_MIDI (app.c:842) takes MUTEX_MIDIOUT (845) -> SEQ_CORE_Handler + SEQ_MIDI_OUT_Handler (851). The Handler drain (seq_midi_out.c:643-661) pops timestamp-due items head-first from the sorted midi_queue and calls callback_midi_send_package(item->port, item->package) FIRE-AND-FORGET at line 655 (return value ignored; the passive capture tee at 659 runs after). Default callback = MIOS32_MIDI_SendPackage (BLOCKING, seq_midi_out.c:192); during capture re-sim it is SEQ_CORE_CapSpanSink (seq_core.c:2307, memory-only, never touches UART); during MIDI export it is Hook_MIDI_SendPackage (seq_midexp.c, file-buffer only). For UARTx ports MIOS32_MIDI_SendPackage dispatches at mios32_midi.c:538 to MIOS32_UART_MIDI_PackageSend (mios32_uart_midi.c:327) whose loop 'while( (error=MIOS32_UART_MIDI_PackageSend_NonBlocking(...)) == -2);' (331) is DEAD today because PackageSend_NonBlocking can never return -2: at line 306 it calls MIOS32_UART_TxBufferPutMore - the BLOCKING wrapper (mios32_uart.c:716) - whose 'while( (error=MIOS32_UART_TxBufferPutMore_NonBlocking(uart, buffer, len)) == -2 );' at line 720 is WHERE THE BUSY-WAIT ACTUALLY LIVES. TxBufferPutMore_NonBlocking returns -2 when tx_buffer_size+len >= MIOS32_UART_TX_BUFFER_SIZE (=64, include/mios32/mios32_uart.h:37, no app override in mios32_config.h); the spin runs with interrupts enabled and terminates only as the USART TXE ISR drains bytes at 31250 baud = ~320us/byte. So the 'case -2: return -2' at mios32_uart_midi.c:308 and the '-2: caller should retry' header contract (256-257) are both dead code - the review's core claims CONFIRM (its line numbers 306/716/665/649 have drifted only slightly: the Handler send is now at 655). IMPACT: a tick burst >64 bytes to one DIN port makes the +4 task spin in-place at line rate for the excess (e.g. 100-byte burst ~ 12ms) while HOLDING MUTEX_MIDIOUT: SEQ_CORE_Tick service (same task) is delayed -> note-timing glitch exactly at the busiest moment; +3 hooks and +2 UI work that takes MUTEX_MIDIOUT (live pads via SEQ_LIVE_PlayEvent, LCD messages) stalls behind it. The bytes cannot leave faster than line rate either way - the defect is WHERE the wait happens (in-place spin at +4 with the mutex held) rather than a deferred queue drain. WHY THE REVIEW'S SUGGESTED FIX IS WRONG (re-derived): swapping line 306 to MIOS32_UART_TxBufferPutMore_NonBlocking (1) does NOT remove the +4 busy-wait - the emission path enters via the BLOCKING MIOS32_MIDI_SendPackage -> MIOS32_UART_MIDI_PackageSend, so the currently-dead while(==-2) at line 331 simply becomes the new spin, one level up; and (2) INTRODUCES MIDI-stream corruption: PackageSend_NonBlocking mutates running-status state BEFORE the put - RS_Reset at 276 (sets rs_last=0xff), 'rs_expire_ctr=0' at 295, and 'rs_last[uart_port] = package.evnt0' at 302-303. On the retry (line 331 loop or any app-level retry), 'package.evnt0 == rs_last' now matches at line 285, the RS-optimisation branch strips the status byte (buffer loses evnt0, --len at 288) even though that status byte NEVER reached the wire (the put failed) -> the receiver interprets evnt1/evnt2 under the previous on-wire status -> wrong notes/CCs on external synths. rs_optimisation defaults to ALL-ON (mios32_uart_midi.c:102) and is a user-facing option (seq_ui_opt.c:732, persisted in MBSEQ_GC.V4 via seq_file_gc.c:349), so this hazard is live by default. WHAT A FUTURE SAFE FIX NEEDS (3 coupled layers, ~4-5 edits across 3 files): [L1 driver, mios32/common/mios32_uart_midi.c] make the -2 path real AND retry-safe: early-return -2 BEFORE any RS mutation when the FIFO cannot take the package - 'if( MIOS32_UART_TxBufferFree(uart_port) <= len ) return -2;' right after computing len (uses the pre-RS-strip len: conservative by at most 1 byte, costing one extra 1ms deferral; MIOS32_UART_TxBufferFree is mios32_uart.c:589). Line 306 may then stay blocking as a backstop for the residual check-to-put race (bounded: app senders serialize on MUTEX_MIDIOUT, only the TXE ISR touches the FIFO concurrently, and it only DRAINS), or switch to the _NonBlocking variant plus an rs_last/rs_expire_ctr snapshot-restore on -2 for full correctness. [L2 emission, modules/sequencer/seq_midi_out.c] Handler drain treats -2 as 'stop this pass, leave item at queue head, retry next 1ms tick' - structurally easy because the send at 655 happens BEFORE the item is unlinked, so 's32 st = callback_midi_send_package(...); if( st == -2 ) break;' is sufficient and loses nothing (no duplicate: nothing entered the FIFO, RS untouched). Defer-not-drop honors 'missing note, never stuck' strictly better than any drop policy: dropping is only safe for NoteOns (a dropped Off = stuck note), so type-aware dropping is strictly more complex than deferring. [L3 callback semantics] the drain only ever sees -2 if it sends via MIOS32_MIDI_SendPackage_NonBlocking - but the SAME callback pointer is used by SEQ_MIDI_OUT_FlushQueue (579), whose note-offs MUST be guaranteed (a -2 drop there = stuck notes on stop). Either give FlushQueue its own bounded retry ('while( callback(...) == -2 );' - behavior-identical to today's in-driver spin, and acceptable: explicit stop gesture, worst case = FIFO drain time), or add a second callback pointer (callback_midi_send_package_nonblocking, default MIOS32_MIDI_SendPackage_NonBlocking, +4B .bss) used only by the Handler drain; the capture (SEQ_CORE_CapSpanSink) and export (Hook_MIDI_SendPackage) hooks never return -2 (verified: memory/file-buffer sinks) but any -2 from a future hook would infinite-loop a FlushQueue retry - must be documented at the callback contract. VALIDATION REQUIRED (why HOLD): saturate one DIN port on the real rig (16 tracks + dense CC to a single UART), verify (a) no stuck notes on stop/flush, (b) RS correctness heard/analyzed on an external DIN synth with RS optimisation both on and off, (c) tick stability under overload, (d) cross-port head-of-line behavior (USB items behind a saturated DIN head now deferred >=1ms - benign vs today's global stall, but a behavior change). The USB-based HIL harness cannot observe DIN-wire RS correctness, so this is by-ear/analyzer work on hardware. Sustained overload eventually exhausts the 256-slot scheduler pool (pre-existing overload behavior, see MIDI-scheduler-pool memory note) - unchanged by this fix. VERDICT RATIONALE: defect real and reachable, no P0/P1 urgency at current usage (needs a >64-byte single-port burst), and the minimal SAFE fix is a cross-layer restructuring of shared platform/module code with hardware-gated validation - per the fork's discipline that is a deliberate future work item, not a quick patch.

## #46 — BSL flash write erases off-base and never verifies (silent brick risk)

**Verdict:** HOLD

**Anchors:** bootloader/src/bsl_sysex.c: BSL_SYSEX_WriteMem (line 533); STM32F4 erase loop lines 566-605 (exact-base test line 574, flash_erase_done bitmask lines 67/579-589, FLASH_START_ADDR reset line 581); program loop lines 607-628 (FLASH_ProgramWord line 615, cache resets 624-625, verify TODO line 627); ACK/NAK plumbing BSL_SYSEX_Cmd_WriteMem END state lines 342-376 (DISACK on WriteMem error line 364-366, retry-flush comment 372-374); flash_sector_map lines 52-65; bsl_sysex.h BSL_SYSEX_MAX_BYTES=1024 line 26; deployment chain bootloader/updater/app.c lines 32-33 (MBHP_CORE_STM32F4 uses pre-built bsl_image_STM32F4DISCOVERY.inc)

**Risks / reachability:** Fix is UNREACHABLE from the app build: bsl_sysex.c is only compiled into the BSL binary (bootloader/src/Makefile.bsl_STM32F4DISCOVERY et al., line 19) and the running copy is the v1.018 image in flash sector 0, last touched in repo 2014-01-10 (2f958035); no post-review wave (ff2505c5/905f93a3/4b4fbd71/417cd864/fb0f76e6) touched bootloader/. Deploying ANY fix means rebuilding the BSL with the current toolchain (binary drift far beyond the fix vs the shipped image), regenerating bsl_image_STM32F4DISCOVERY.inc, and running the updater which live-reflashes sector 0 ('don't power off!!!') on the user's only instrument — failure bricks the MIOS Studio upload path (recovery only via ST-LINK / ROM DFU ladder). Also: the user's remembered upload corruption (cured by an md5-identical rebuild) is more plausibly link-level; the per-block 7-bit checksum already NAKs transit corruption before WriteMem runs, so a BSL verify-after-program would catch program-level corruption but is not established as the cure for that incident.

**Full derivation & fix plan:**

MECHANISM (verified against current source, all line numbers current): (1) BSL_SYSEX_WriteMem STM32F4 branch (bsl_sysex.c 566-628). The erase loop (573-604) scans flash_sector_map[12][3] (52-65: sectors 0-3 = 16KB @0x08000000/4000/8000/C000, sector 4 = 64KB @0x08010000, sectors 5-11 = 128KB @0x08020000..0x080E0000 — correct STM32F407 1MB layout; sector 0's base is deliberately the 0xffffffff sentinel so the BSL can never erase itself) and erases ONLY when `addr == flash_sector_map[sector][0]` exactly (574). The flash_erase_done bitmask (67) suppresses re-erase of an already-erased sector within a BSL session (585-589) and is reset when addr == FLASH_START_ADDR = 0x08004000 (581-583) so a restarted upload re-erases; this exists for the erase->1s->MIOS-Studio-retry case (comment 575-578). (2) If a block's start address is inside a sector but not its base, NO erase runs; FLASH_ProgramWord (615) then programs un-erased cells. STM32F4 NOR flash programming can only clear bits, so the result is (old AND new); the F4 flash controller does not flag not-erased targets, so status == FLASH_COMPLETE and the block is ACKed (Cmd_WriteMem 364-370) — silent corrupt image. A second unhandled shape: only the block START is tested, so a 1024-byte block spanning a sector base (e.g. addr 0x08007C00 crossing 0x08008000) programs the next sector's head without ever erasing it. (3) Line 627 confirms verify is still a TODO; there is no read-back, so neither the AND-corruption nor a marginal program failure is ever detected on-device. PROTOCOL: the BSL CAN NAK a block — Cmd_WriteMem's END state returns DISACK(-error) on WriteMem failure (364-366) and flushes it immediately 'important for retry handling' (372-374); short blocks already DISACK with a '(retry)' debug message (345-351). So a verify-failure NAK is protocol-compatible and MIOS Studio retries/aborts visibly instead of trusting a corrupt ACK. EXPOSURE: MIOS Studio sends contiguous blocks of BSL_SYSEX_MAX_BYTES = 1024 (bsl_sysex.h:26) starting at FLASH_START_ADDR; since 1024 divides 0x4000 and every F4 sector base is a multiple of 0x4000, every sector base is exactly a block start in every normal upload — the bug needs a foreign host, a resumed/partial upload, or a gap-containing image to fire. REACHABILITY (the deciding fact): bsl_sysex.c is listed only in bootloader/src/Makefile.bsl_* (line 19 of each); a repo-wide grep finds no app referencing it (only the review doc). During an upload the app reboots into the BSL in sector 0 and the FLASH-resident v1.018 code handles Write-Mem; the deployment vehicle is bootloader/updater, which embeds the PRE-BUILT binary bsl_image_STM32F4DISCOVERY.inc (app.c 32-33 maps MIOS32_BOARD_MBHP_CORE_STM32F4 to that image) and byte-compares/reprograms sector 0 at runtime. Editing the .c does not change the .inc, so even building+flashing the updater today would deploy the OLD image. FUTURE FIX SHAPE (write-down for a deliberate BSL-update session): (a) Read-back verify — after the two cache resets (624-625), add: `if( MEM32(addr) != data ) { FLASH_ClearFlag(0xffffffff); return -MIOS32_MIDI_SYSEX_DISACK_WRITE_FAILED; }` (MEM32 macro exists at line 28). Behavior-identical on every good upload; converts silent corruption into a DISACK the host surfaces. (b) Erase-keying — do NOT switch to erase-the-containing-sector: a mid-sector first-touch erase would wipe the sector's already-programmed head, and the BSL cannot stage 128KB sectors in RAM; a resumed upload would then verify clean word-by-word yet leave a blank sector head (verified-but-incomplete image). The provably-conservative change is NAK-not-heal: before the program loop, if the target range lies in flash and the containing sector's flash_erase_done bit is not set (i.e. no erase has happened this session for that sector), return -MIOS32_MIDI_SYSEX_DISACK_WRITE_FAILED. That invariant holds for every legitimate MIOS Studio upload (each sector's first block IS its base, which sets the bit) so behavior is unchanged for the real workflow, while off-base first-touches become explicit host-visible failures instead of AND-corruption. Extend the base test to per-sector range intersection only for setting/checking the bit, keeping sector 0 excluded (the addr >= FLASH_START_ADDR gate at 540 already excludes it; keep the 0xffffffff sentinel untouched). (c) VALIDATION LADDER (required before touching the instrument): 1. build BSL via Makefile.bsl_STM32F4DISCOVERY with the current arm-none-eabi toolchain and diff the disassembly against the shipped bsl_image_STM32F4DISCOVERY.inc to bound toolchain drift; 2. bench-validate on a sacrificial STM32F4DISCOVERY board flashed via ST-LINK: normal upload, checksum-corrupt retry, DISACK retry, erase->1s retry, deliberate off-base Write-Mem (must NAK), power-cycle mid-upload; 3. regenerate the .inc (gen_inc_file.pl / release.sh), build the updater, and only then run it on the instrument with the recovery ladder (ST-LINK + ROM DFU, per memory reference-firmware-upload-recovery.md) on hand; 4. re-upload MBSEQV4P and rerun HIL. Until a session budgets that ladder, the correct disposition is HOLD — the patch is small but the deployment is the risk, and it cannot be proven safe without hardware.
